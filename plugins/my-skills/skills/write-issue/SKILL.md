# write-issue

ユーザーのざっくりした要望を、**後で `implement-issue` に番号を渡すだけで実装が始められる**くらい完全なGitHub Issueに仕上げて登録するSkill。

## 基本方針

- 「実装者が追加で質問しなくても着手できる」状態をゴールにする。
- 情報が足りなければ**勝手に埋めず、1問ずつ**ヒアリングする。
- 本文の作法は固定テンプレに従い、抜け漏れを防ぐ。

## 手順

1. **種別を判定する**：バグ / 機能追加 / 改善 / リファクタ のどれか。判断が付かなければユーザーに確認。

2. **不足情報をヒアリングする**（仕様が曖昧なときのみ）。一度に詰め込まず1問ずつ。例：
   - バグ：再現手順・期待挙動・実際の挙動・環境（staging/production）・関連ログ
   - 機能：目的・対象ユーザー・受け入れ条件・対象範囲
   - 影響する既存機能や連携先（例：kintone / texpress などの連携箇所）

3. **テンプレに沿って本文を生成する**（下記）。

4. **ラベルと優先度を提案する**。優先度は **Critical / High / Middle / Low** の4段階で、理由を一言添える。

5. **登録前に本文をユーザーに見せて確認を取る**。OKが出たら `gh` で登録：
   ```bash
   gh issue create --title "<タイトル>" --body-file <一時ファイル> --label "<labels>"
   ```
   登録後はIssue URLと番号を返し、「`implement-issue <番号>` で着手できます」と案内する。

## 本文テンプレート

### バグ報告

```markdown
## 概要
<1〜2文で何が問題か>

## 再現手順
1.
2.
3.

## 期待する挙動


## 実際の挙動


## 環境
- 対象: staging / production
- 関連: <kintone / texpress など>

## ログ・スクショ
<あれば>

## 受け入れ条件 (Acceptance Criteria)
- [ ]
- [ ]

## 対象範囲・関連ファイル
<分かる範囲で。なければ「調査が必要」と明記>

## 技術メモ
<原因の仮説や注意点があれば>

## 優先度
Critical / High / Middle / Low — <理由>
```

### 機能追加・改善

```markdown
## 背景・目的
<なぜ必要か。解決したい課題>

## やりたいこと
<実現したい挙動を具体的に>

## 受け入れ条件 (Acceptance Criteria)
- [ ]
- [ ]

## 対象範囲・関連ファイル
<触る予定の領域。連携先があれば明記>

## 技術メモ
<設計方針・既存処理との関係・注意点>

## スコープ外
<今回はやらないこと>

## 優先度
Critical / High / Middle / Low — <理由>
```

## 注意

- 受け入れ条件は必ず「テスト可能な形」で書く（曖昧な表現を避ける）。
- 対象範囲が不明なときは空欄にせず「要調査」と明記して、`implement-issue` 側に調査が必要だと伝わるようにする。
