# implement-issue

Issue番号を受け取り、内容を読んで実装まで進めるSkill。引数 `$ARGUMENTS` がIssue番号。

## 引数

- Issue番号（必須）：例 `123`。先頭に `#` を付けた `#123` 形式でもよい。
- `--worktree`（`-w`、任意）：作業を git worktree 上で行う。指定すると現在のチェックアウトを汚さず、別ディレクトリで隔離して実装する。
- **追加指示（任意）**：Issue番号とフラグ以外の自由記述テキストは、すべて実装に対する追加指示として扱う。Issue本文を補足・上書きする形で実装方針に反映する。

`$ARGUMENTS` の解釈ルール：
- 先頭で見つかった数値（`grep -oE '[0-9]+' | head -1`）を **Issue番号** とする。`#123` のように `#` が付いていても数値部分だけを取り出す。
- `--worktree` / `-w` を **フラグ** として認識する。
- 上記（Issue番号は `#` 付きの場合も含めて）を取り除いた残りのテキストを **追加指示** とみなす（空ならなし）。

例：
- `123` / `#123` … Issue 123 を素直に実装
- `123 --worktree` / `-w #123` … worktree 上で実装
- `#123 テストは vitest で書いて、既存のutilを使い回して` … 追加指示付き
- `-w 123 まずは最小実装だけ、リファクタは別PRにする` … worktree + 追加指示

## 対象Issueの内容

以下が `gh` で取得した対象Issueの内容（実行時に自動で差し込まれる。引数からIssue番号だけを抜き出して参照する）:

!`gh issue view $(echo "$ARGUMENTS" | grep -oE '[0-9]+' | head -1)`

## 手順

1. **内容を把握する**：上記のIssue本文から「受け入れ条件」「対象範囲」「技術メモ」を読み取る。
   - **追加指示があれば最優先で反映する**：`$ARGUMENTS` から Issue番号・フラグを除いた自由記述テキストは、ユーザーからの追加指示として扱う。Issue本文と矛盾する場合は追加指示を優先し、補足の場合は両方を満たす。何を追加指示として解釈したかを着手前のメッセージで簡潔に明示する。
   - 受け入れ条件が曖昧、または対象範囲が「要調査」の場合は、まずコードを調査する。
   - それでも実装方針が一意に決まらない重要な不明点があれば、**着手前に1問だけ**ユーザーに確認する（細かい点は確認せず進める）。

2. **ブランチ（または worktree）を作る**：ブランチ名は `issue/<Issue番号>-<短い英語の要約>` の形式。
   - 通常：`git switch -c issue/<番号>-<要約>` で現在のリポジトリ上にブランチを作る。
   - `--worktree`（`-w`）指定時：git worktree を使って隔離した作業ディレクトリを作る。
     - **必ずそのリポジトリのデフォルトブランチの最新からブランチを切る**（`main` / `develop` / `master` などリポジトリにより異なる）。デフォルトブランチを確認し、リモートの最新を取得してから、それを起点に worktree を作る。
     ```bash
     DEFAULT_BRANCH=$(gh repo view --json defaultBranchRef -q .defaultBranchRef.name)
     git fetch origin "$DEFAULT_BRANCH"
     git worktree add ../<リポジトリ名>-issue-<番号> -b issue/<番号>-<要約> "origin/$DEFAULT_BRANCH"
     ```
     - 以降の実装・テスト・コミット・PR作成はこの worktree ディレクトリ内で行う。
     - 作業完了後（PRマージ後など）に不要になったら `git worktree remove <パス>` で後片付けすることを要約で案内する。

3. **実装する**：
   - リポジトリ既存のコーディング規約・ディレクトリ構成に従う。
   - 受け入れ条件を1つずつ満たしていく。
   - 連携箇所（kintone / texpress など）に触れる場合は、staging/productionの設定差に注意する。

4. **テストを追加・実行する**：
   - バグ修正なら、まず再現するテストを書いてから直す（TDD寄り）。
   - 既存テストが通ることも確認する。

5. **UI変更があればPlaywrightで動作確認する**：
   - 変更ファイルパスに `routes/` `components/` `pages/` `views/` や `.tsx` `.jsx` `.vue` などフロントエンド由来のパス・拡張子が含まれる場合のみ実施する。バックエンド・API・スキーマのみの変更なら本ステップは省略してよい。
   - dev サーバーが起動していなければ `lsof -iTCP -sTCP:LISTEN -P` 等で確認し、起動していなければユーザーに起動を依頼する（例: `! pnpm dev`）。起動を待てない場合はスキップし、要約で理由を明記する。
   - Playwright MCP（`mcp__playwright__browser_navigate` / `browser_take_screenshot`）が使えない場合は、そのことを要約に明記して本ステップをスキップする（実装自体は止めない）。
   - 受け入れ条件ごとの代表的な画面状態を `mcp__playwright__browser_navigate` で開き、`mcp__playwright__browser_take_screenshot` でPNGを保存する。ファイル名は `issue<Issue番号>-<画面>-<状態>.png`。
   - 各キャプチャをReadで目視し、受け入れ条件どおりの表示か検証する。ズレていれば実装を修正してから撮り直す。
   - 動画記録は可能であれば追加で試みる（Playwright MCP に録画機能がある場合）。取得できない・不安定な場合はスクリーンショットのみで進め、動画なしである旨を要約に記す。
   - 撮ったキャプチャ（画像・動画）はリポジトリ管理外の一時ファイルとして扱い、削除せず残しておく（PR作成時に案内するため）。

6. **コミットする**：本文に `Closes #<Issue番号>`（`$ARGUMENTS` の先頭数値）を入れて、マージ時にIssueが自動クローズされるようにする。フラグや追加指示テキストは含めない。

7. **PR作成前にレビューと整理を行う**：
   - `/code-review` を実行して、変更差分のバグや改善点を洗い出す。指摘があれば対応する。
   - `/simplify` を実行して、変更コードの重複排除・簡素化・効率化を行う。
   - レビュー・整理で生じた修正はコミットしてからPR作成に進む。
   - コード修正でUI表示に影響する変更があった場合は、手順5のキャプチャを撮り直す。

8. **PRを作成する**：原則 **draft** で作成する（`--draft` を付ける）。
   ```bash
   gh pr create --draft --title "<タイトル>" --body "<受け入れ条件の達成状況 + Closes #<Issue番号>>" --assignee kenta-takeuchi
   ```
   - PR本文には「何を・なぜ変えたか」「受け入れ条件のチェック結果」「動作確認の方法」を書く。
   - 手順5でキャプチャを取得した場合、「## 動作確認」セクションを設け、キャプチャごとに見出し＋HTMLコメントのプレースホルダーを置く（`gh` CLIではローカル画像を直接アップロードできないため）：
     ```markdown
     ## 動作確認

     ### <状態の説明>

     <!-- ここに issue<番号>-<画面>-<状態>.png を貼り付け -->
     ```
   - ユーザーから「draftにしない」「ready for reviewで」と明示的に指示された場合のみ `--draft` を外す。

9. **最後に要約を返す**：実装内容・変更ファイル・残課題（あれば）に加えて、以下を報告する。
   - UI動作確認を実施したか（省略した場合はその理由）
   - 保存したキャプチャ（画像・動画）のファイル名と保存場所、動画が撮れなかった場合はその旨
   - PR編集画面で各プレースホルダー位置にキャプチャをドラッグ&ドロップするようユーザーに案内する

## 注意

- Issueの受け入れ条件をすべて満たすまで完了としない。満たせない条件があれば、その理由を明記する。
- 想定外に大きい変更になりそうなら、いったん手を止めて方針をユーザーに確認する。
- `gh` が未認証の場合は `gh auth login` を案内する。
